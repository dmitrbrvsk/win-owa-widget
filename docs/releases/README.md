# Описания релизов

Каждый опубликованный релиз имеет отдельный файл `v<версия>.md`. Его содержимое становится описанием на GitHub: сначала изменения для пользователя, затем раскрывающийся блок установки и проверки файлов.

## Новая версия

1. Обновите `version` в `package.json` и выполните `yarn install`, чтобы проверить согласованность `yarn.lock`.
2. Скопируйте [TEMPLATE.md](TEMPLATE.md) в `docs/releases/v<версия>.md`.
3. Опишите изменения по сравнению с предыдущим релизом: новые возможности, исправления и важные ограничения. Замените все `TODO` и `<версия>`, проверьте имена файлов установки. Удалите разделы, которые не нужны этой версии.
4. Запустите `node scripts/release-notes.mjs --check` и обычные проверки проекта.
5. После отправки в `master` workflow Build проверит описание и передаст его вместе с артефактами сборки в публикацию. Без файла текущей версии, списка изменений или с оставшимися заглушками проверка завершится ошибкой.

Текст описания не берется из названий коммитов и не генерируется общим шаблоном о продукте. Он хранится рядом с кодом и проверяется вместе с изменениями.

## Исправление опубликованного описания

Измените соответствующий файл и отправьте его в `master`. Workflow **Release notes** обновит текст существующего опубликованного релиза. Его также можно запустить вручную через GitHub Actions.

Синхронизация меняет только поле описания: не создает и не удаляет релизы, не переставляет теги, не меняет установщики, даты публикации или статус последнего релиза. Для версии, которая еще не опубликована, она ничего не создает; описание будет использовано обычной публикацией Build.

## Общая история изменений

При подготовке версии обновляйте также [CHANGELOG.md](../../CHANGELOG.md): кратко опишите заметные пользователю изменения и перенесите их из раздела «Не выпущено» под номер версии. Дата — день публикации по московскому времени. В описании GitHub Release остаются подробности версии и инструкции установки, в CHANGELOG — общая история без повторяющихся инструкций.

Если CI завершился ошибкой до публикации, исправьте причину и повторите сборку с тем же номером версии. Уже опубликованный номер для другого содержимого не используйте. Подготовленные, но не опубликованные версии не перечисляйте как состоявшиеся релизы; при необходимости поясните пропуск рядом с реально выпущенной версией.
